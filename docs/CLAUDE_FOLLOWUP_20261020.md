# Claude 复审任务：P1–P6 第二轮修复及仍待确定的机制

本文请 Claude 做只读设计复审。项目继续采用 DeepSeek、本地知识库、官方网页检索和 CRAG；此次没有更换模型或重建问答框架。

原方案基于提交 `a6113ee`，见 [NEXT_PHASE_PLAN_FOR_CODEX.md](NEXT_PHASE_PLAN_FOR_CODEX.md)。P0 和 P1–P6 首轮实现后，我们曾授权执行 24 次真实问答；本轮根据该录制暴露的问题继续修复，运行版本为 `phase1.8.4-grounded-recovery`。**本轮只进行了代码修改、离线诊断和自动测试，没有生成新的 24 次或 160 题端到端模型回答。** 本次提交的代码和文档以所在仓库提交为准，旧方案行号不再直接适用。

## 1. 用户要解决的业务目标

用户需要系统对一类问题持续给出完整、有证据的回答，不能只让固定 160 题出现引用。典型任务包括：

- 分清台风路径、气象预警、海洋警报，并提供各自实际查询入口。
- 区分政府过渡期救助、冬春救助和保险赔付，说明各自文件依据、办理对象和程序。
- 根据官方资料说明灾后疾病传播风险，分别回答风险关系、积水清理和个人防护，避免把鼠媒疾病归到蚊媒。
- 给出养殖设施加固方法，同时保留个人能否获赔所需的真实保单与核定条件。
- 对指定地区、时间的预报、潮位和活动问题，交付具体数据、单位、基准、有效时间及来源；缺少业务输入时明确指出缺什么。

当前重点是修复“检索已经取得相关证据，但校验、恢复、归属或完整性判定仍损坏答案”的系统问题。真实数据缺口另行记录，不能用泛化解释或引用数量替代业务交付。

## 2. 首轮真实录制暴露的根因，以及本轮修改

### 2.1 局部恢复丢掉全题身份，却保留全题生成布局

旧代码只把待补子问传给 grounding；若仅剩一个子问，其余主题的事实容易被兜底分到该子问。与此同时，重写提示仍含完整问题、旧布局和已答正文，所以模型把兄弟子问重新输出。录制中出现“气象台风预警”标题下实际发布海洋海浪查询渠道，以及保险问题下面重复网箱、池塘加固措施。

本轮把完整子问注册表与补写权限分开：`facet_contract` 始终保留全量身份，`target_fids` 只限定本次可以补写的子问。局部问题、布局和检索查询同步裁剪；冻结兄弟只提供身份与哈希，不把正文当成重写草稿。恢复校验在完整注册表上运行，再拒绝越权、对象或意图冲突的原子；重复事实去重，并一并清理失效的归纳前提链。

入口：[answer_pipeline.py 的 repair_payload](../marine_kb/answer_pipeline.py#L27)、[recovery.py 的 recover_locally](../marine_kb/recovery.py#L39)、[facet_delivery.py 的 semantic_match](../marine_kb/facet_delivery.py#L41)。

### 2.2 “有网站”“有动作词”被错误计为完整交付

旧门槛把网站、平台等相同词同时作为渠道名称和访问路径；清积水措施也可填防叮咬子问，过敏或一般防护措辞可凑出传染风险关系。因此旧回答有至少 3 个经阅读确认的假完整反例：C2、M1_extra_2、M1_extra_3。

本轮分别核对业务对象、发布体系和回答意图。渠道名称与具体进入方式分开；方法步骤去重，扩充穿衣、纱窗、蚊帐等真实动作；感染风险要回答感染或传播这一结果，不能拿无关风险词替代。用户渲染采用中文缺项标签和可读日期，不直接暴露内部字段或 Python 字典。

入口：[semantic_match](../marine_kb/facet_delivery.py#L41)、[_channel_parts](../marine_kb/facet_delivery.py#L89)、[covered_outputs](../marine_kb/facet_delivery.py#L185)、[evaluate_delivery](../marine_kb/facet_delivery.py#L273)。这些仍是最低交付检查，**不是独立的事实正确性评估器**。

### 2.3 已取到的正文、短导航和限定语在校验中丢失

证据对象升级后，来源 URL 主要位于 `doc_card.url`，关系守卫却仍读旧字段，导致官方疾控资料被误报为非权威来源。网页导航“天气预警”“台风发布”只有四字，被通用短引文规则拒绝。“第 6.3 节”等定位文本又可能被当成物理量。地域范围或例示限定被删除后，还可能留下看似全国通用的地方办理内容。

本轮统一读取规范文档卡 URL；短导航例外要求真实 passage、原文偏移及哈希一致，只支持查询操作，不能证明解除预警或允许出海；章节定位与物理数值分开；保留明确绑定的地域限定。引号、书名和配套条件内的标点不再机械拆句。

入口：[relation_guard.py 的 health_authority](../marine_kb/relation_guard.py#L23)、[typed_grounding.py 的 prepare_draft](../marine_kb/typed_grounding.py#L188)、[_grounded_display](../marine_kb/typed_grounding.py#L431)；短导航与量纲边界见 [test_followup_pipeline_contracts.py](../tests/test_followup_pipeline_contracts.py) 和 [test_grounding_followup_regressions.py](../tests/test_grounding_followup_regressions.py)。

### 2.4 未问缺项与真实缺项绑在一个字符串中

“独立访问网址”等名词缺项因为不含“缺少”，被分类为 `unclassified`，即使覆盖审查准确指出未问也不能处理。疫情实况先因“当地”被归为地方规范。保险缺项又把承保范围、投保条件、可选保费补贴和理赔流程绑成一串，导致全部随个人资格受保护。局部补写后，最终缺项仍来自初稿快照。

本轮按原始子问核对缺项；名词型输入也分类。少数高置信未问实况可转为不阻断交付的范围说明。混合列表仅在每项均为独立要求时分解，括号内业务对象、书名和条件句不机械拆开。明确要求的网址、实际个人资格、当日状态、数值、单位与基准继续保护；审查不能任意删除。初稿、局部稿和最终原子集同步应用规则，新证据补全后再核对缺项生命周期，并重算最终交付与正文。

入口：[scope_gate.py 的 gate](../marine_kb/scope_gate.py#L184)、[gate_atoms](../marine_kb/scope_gate.py#L268)、[reconcile_gap_resolution](../marine_kb/scope_gate.py#L311)、[answer_pipeline.py 的 organized_v2](../marine_kb/answer_pipeline.py#L188)。范围修正本身不允许升级完整性。

### 2.5 有据归纳没有足够表达能力，审查又可能互相冲突

首轮受限归纳主要支持类别、依据、发文主体、程序的固定比较，难以表达“风险不证明已经发生”或更自然的制度区别。旧模型也常把本可归纳的句子标为直接事实或 unsupported，缺少必要的前提和推理字段。

本轮扩展用途、适用对象、触发条件的明确比较，以及 `risk_not_occurrence`。程序要求每个关系槽位在已保留的原子和引文中出现，保留条件和否定，不接受以机关不同直接证明制度不等价，也不把风险不足以证明暴发改写成当地没有疫情。

同一逐句审查内，相同断言、相同子问和相同引用出现相反判定时，可在预算内复查一次。初稿或合并后的覆盖审查另有争议时，程序按原段和原子逐字定位暂缓发布争议事实及依赖归纳；无法唯一定位时记录歧义并保持不完整，不扫掉无关兄弟内容。这仍是临时处理机制，跨阶段审查谁裁决、如何保住正确归纳，需要本次重点复审。

入口：[find_judge_conflicts](../marine_kb/typed_grounding.py#L297)、[resolve_judge_conflicts](../marine_kb/typed_grounding.py#L333)、[_check_synthesis](../marine_kb/typed_grounding.py#L490)、[_check_risk_not_occurrence](../marine_kb/typed_grounding.py#L601)、[withhold_disputed_atoms](../marine_kb/answer_pipeline.py#L87)。

## 4. 请 Claude 重点决定的四个设计问题

### A. 跨阶段审查分歧如何裁决

请检查：逐句审查认定有支持，但覆盖审查认定同一内容无支持，或恢复后出现相反判定时，能否构造共享的断言—证据—子问身份及有限复查机制？

请给出最小实现方案：冲突键、可比条件、何时只重核一个原子、何时必须改写、超时或两次仍不一致时发布哪些内容。必须防止“后一个审查覆盖前一个审查”再次造成整句丢失；也不能为了保住结论而默认相信任何一个模型。当前精确定位暂缓发布是否过度保守、是否仍可能留下定位不清的争议内容，请分别列正反例。

### B. 有据归纳怎样扩展而不变成常识放行

请设计适用于制度比较、信息产品比较、风险与实况区别的有限归纳协议。需要明确：最少前提、关系槽位、条件与否定继承、跨文档适用范围、可生成的结论边界，以及程序能确定性检查的部分。

请重点评估现有封闭句式是否仍导致误删；如何让模型在首次生成或审查时提供可校验前提，处理那 22 个旧记录缺证明的类型。不得给每个题号写一个结论模板；不得因所有实体在正文出现就放行新因果、个人获赔、许可、数值或法律效力。

### C. 最小完整交付怎样从关键词升级为通用机制

请评估当前 `semantic_match` 和 `covered_outputs` 的上限，并提出既能按业务对象与动作检查、又不会无止境增加关键词的方案。特别区分：

- 告诉用户哪个平台，与提供实际能进入的查询方式。
- 给出措施，与真正回答疾病传播风险或是否意味着暴发。
- 解释一般理赔条件，与判断某个人是否获赔。
- 列分项历史指标，与推断总体灾损更轻或更重。

请提出可逐步接入现有代码的结构化输出或断言图，而非整体换框架。必须说明如何检验遗漏、错误归属、真实缺项召回与 false_full；最小交付检查和事实支持检查继续分开。

### D. 正文恢复与后续真实验证如何安排

请就 17 个未匹配正文记录提出追查顺序与证据快照改进；不能把修改后的网页拿来替代旧时刻证据。对 G1 边界变化，指出最小新判定输入及前后结果如何比较。

请提出下一轮小规模固定清单，分别覆盖原题、同类改写、多子问顺序变化、地点与日期纠正、缺证据负例；注明哪些属于离线确定性测试、哪些必须真实 DeepSeek 问答、预计涉及多少次调用。新增调用需由项目方确定范围后执行。本轮没有申请或执行新的付费测试。
