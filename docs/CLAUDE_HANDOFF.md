# 海洋灾害知识问答系统待解决问题与方案设计交接

## 一 任务和当前结论

用户希望 Claude 先诊断现有系统并设计解决方案，再交给 Codex 执行。本轮没有继续修改问答算法，也没有重跑 160 题。仓库为 2026 年 10 月 19 日 `phase1.8.3-public-evidence` 的脱敏源码快照。

系统已经具备本地知识库、官方联网检索、网页正文阅读、预报与历史数据工具、多轮对话和回答校验。主要问题已经不是“有没有调用大模型”，而是证据经过多次选取、生成、审查和恢复后，是否仍覆盖用户真正问的内容。有些公开资料可回答的问题仍退化成泛泛解释或零碎摘录；另一些业务问题确实缺数据。两者需要分开治理。

目标面向 160 题代表的业务类型和未见改写题，不针对题号编写答案。回答以用户可读的结论和操作/数据为主，必要时用分项或表格，并能回查原始依据。历史参考、当前状态、假设计算和正式发布必须各自保持准确含义。

## 三 当前架构与代码阅读顺序

1. `server.py` 装配 Flask、知识库、预报和台风服务；`production_server.py` 使用 waitress。默认端口和启动脚本端口不同，按环境配置确定。当前用户在统一历史台风地图页面使用系统。
2. `frontend/index.html`、`frontend/map_assistant.js` 和 `marine_kb/chat_api.py` 构成统一页面及 `/api/assistant/ask`。后端保留对话上下文，前端支持根据回答继续追问。不要重新拆成“简洁问答”和地图两个用户入口。
3. `marine_kb/bootstrap.py` 创建 `KnowledgeStore`、可选语义索引、资料外发授权层、`OfficialWebSupplement` 和问答服务。当前构造参数包含 `search_policy='always'`、`crag_enabled=True`；是否可实际联网/调用模型仍受开关与凭据控制。
4. `marine_kb/qa.py` 的 `MarineQuestionService` 是主要问答服务，`_organized_answer` 组织检索证据、模型生成、各类检查与恢复。业务路由可能先调用 `forecast_runtime/` 的确定性工具，再将结果交给回答层。
5. `marine_kb/crag.py` 的 `CorrectiveRetrieval` 做子问题证据评分和有界纠错。现有实现借鉴 CRAG 的检索评价与纠错思想，是项目适配代码，不能当成作者代码原样运行。上下游源编号、段落选择及子问映射需要重点追踪。
6. `marine_kb/public_service_intents.py`、`public_sources.py`、`web_supplement.py` 控制公开服务领域查询词、官方入口、候选页面及正文；`typhoon/web_search.py`、`web_reader.py` 提供网络搜索和读取能力。
7. `marine_kb/evidence_applicability.py`、`evidence_selection.py`、`question_contract.py` 判断对象、地点、时间、版本、问题范围；`coverage_review.py` 与 `answer_completeness.py` 检查子问覆盖。
8. `marine_kb/claim_grounding.py` 的 `review_claim_batches`、`apply_attribution` 做逐项支持审查与恢复；`quantities.py`、`version_claims.py`、`citation_repair.py` 处理数值、效力和引用。`qa.py` 的组合校验/恢复逻辑决定最后保留什么，而不只是最终提示词。
9. `forecast_runtime/` 包括任务计划、路由、获取、解析、存储、天文潮、岸段计算、预警归档、活动与历史比较。阅读 `task_plan.py`、`routing.py`、`service.py`、`answer_facts.py`、`historical_comparison.py`、`official_warnings.py`、`recreation.py`、`activity_rules.py`。
10. `typhoon/` 保留历史路径、相似台风和灾害记录；`spatial_runtime/` 处理地形与人口。空间格网接入不等于已有经过校准的淹没与转移人口模型。

## 四 已确证的失败与待验证根因

### 4.1 已取得资料却在最终校验后丢掉核心答案

真实 G3 问题：“台风后政府的过渡期生活救助、冬春救助和巨灾保险赔付是不是一回事？分别依据什么办理？”

最终实际输出只有：

> 该方案自2024年4月30日起施行[资料4]。
>
> 部分子项的依据尚未核对完整，以上仅保留本次来源能够支持的内容。

这没有回答三项制度的区别与办理依据。记录同时显示 `semantic_evidence_support_failed`，逐句恢复曾考虑 11 项陈述，只保留 1 项。`claim_attribution_recovery.decisions` 给出删除理由，包括“原段未出现完整预案名称”“没有直接概括三项制度不同”“整句混合多项而不能全部支持”。`recovered_completeness_review` 为 `ValueError` 后 unavailable。CRAG 记录显示已选取官方网页且部分子问 supported，最后返回的来源列表却只剩一个。

**确证问题：**最终保留陈述与用户目标不匹配；同一回答同时出现检索子问已支持和最终答案无关的状态；恢复后的覆盖审查不可用。**待验证假设：**证据段落与标题/文号等文档元数据脱节；对可追溯归纳和原文逐字支持没有分层；复合陈述因局部失配整句丢弃；恢复过程的源编号与最终来源重排可能增加不一致。请逐条用代码和 trace 验证，不能直接把所有删除都定性为错误。原生成内容也可能有错误归因。

方案应明确什么属于直接事实、受证据约束的归纳、计算推导和未知状态；对每类给出不同验证方法。修复以最小受支持语义单元为目标，保留正确的兄弟子问，并在恢复后重新验证相关性与覆盖。不把“引用都对但没有回答”当成功，也不通过直接跳过校验保住错误原稿。

### 4.2 将未问的地方专用规则或实时状态当成必答条件

A2 要求温州网箱缆绳、框架、网衣检查步骤，回答已经给出有出处的通用技术步骤，却仍把温州专用规程列为缺项。C3 只问台风路径能否替代气象预警及渠道，回答仍增加“当前发布状态”等缺项。M3 问“蚊子多是否就说明已暴发登革热”，系统在解释不能推出疫情后，又因缺当地监测列 partial。

这些例子有真实回答内容，但审查范围扩大。最近的有界重写和 `unasked_gap` 处理没有完全解决。需要由问题契约控制审查目标，区分“地名背景下的通用方法”“当地现行规定”“某时刻状态”和“个人资格”。精确地方工艺、个体赔付等真正必要条件仍要保留。

### 4.3 可靠网页也可能在回答中产生错误关系

M1 同时引用涉及老鼠、蚊蝇及多种传染病的灾后材料。模型 full 标签和引用存在不能证明疾病传播关系正确。审查需要识别句子的主体、关系、条件和例外，避免把同一段里出现的实体拼成错误因果。医学/法律等专业细节需要对应权威原段，不能只用通用语义相似度验收。

### 4.4 数据连接存在但具体日期查询仍可能没有结果

较早 Q-022 曾对指定预报时段返回“198 岸段可计算 0”，另一个历史对比场景又取得 173 岸段。这些是不同查询/运行记录，不能拿后者证明前者正确。应分别核对起报批次、有效时间、时区、产品过期判断、单位、网格最近点/缺测、缓存及查询截止时刻，然后检查实际计算结果是否进入生成证据。NC 接口存在不等于任意历史/未来日期均可查询。

历史最大增水、最高潮位和经济损失是不同指标。岸段代表点与历史测站不是同站；跨站峰值不能作为同站潮位差；预报场覆盖某时段不等于全场由某一个台风造成。方案要把“有数据但路由/格式/引用丢失”和“这个日期/变量/对象根本无覆盖”分别定位。

### 4.5 联网补充并不是搜索一次就足够

过去存在官方预警渠道、养殖加固、灾后防蚊、救助申请等公开信息没有答好的情况。最后 12 题证明两路检索已经执行，但仍有上述问题。当前需要审查查询改写、正文提取、候选选择、证据压缩、文档元数据、引用编号、按子问覆盖和失败恢复的整体一致性，不能只再加一个 always-search 开关。

## 五 问题分类和数据边界

| 类型 | 可以通过工程或公开来源改善 | 仍需额外核定/业务输入 |
|---|---|---|
| 科普、通用防灾操作、官方渠道 | 官方正文读取、领域检索、清晰组织与关系校验 | 具体疫情/现场状态不能由科普推出 |
| 预案、救助、保险 | 收集正式正文，区分文件标题、文号、生效期和实际办理主体 | 地方现行版本、申请窗口、个体资格、保单及最终赔付 |
| 历史灾害指标与比较 | 原表恢复、文档结构化、事件站点匹配、同指标统计 | 缺失历史观测、完整损失与可比口径 |
| 日期地区预警清单 | 官方清单+正文+更新/解除归档，按当时有效性查询 | 部分浙江接口没有访问凭据；国家源不保证完整省级清单 |
| 预报风浪潮位和活动筛查 | NC 解析、单位时间转换、岸段/站点映射、带来源计算 | SWL 含义及高程基准仍有假设；浴场开放、水质、救生、礁滩返程和船舶条件 |
| 淹没范围与转移人口 | 地形人口预处理、空间叠加与不确定性表达 | 裸地高程、海堤闸泵状态、校准淹没模型、房屋人员台账；100 米人口不是人员名册 |

用户此前允许先按“SWL 为纯增水”等假设打通试算。这些授权并未把假设变成已验证物理含义。模式实际数值与“如何解释和叠加数值”分开记录。不能把真实接口值统称为人工编造，也不能把假设计算包装为正式预警。风速单位、天文潮 1985 基准等也依赖具体产品核定。

本地有浙江地形与人口数据，但未上传大栅格。旧说明可能含早期入库数，实际只读库存见 `local_asset_inventory.json`。1252 条风暴潮站记录是事件—站点记录数，不是独立站点数量。

## 六 Claude 方案需要回答的设计问题

1. 如何建立统一子问题契约，让检索、计算、生成和审查共用稳定目标 ID？如何避免纠错后其他已答子问退化？
2. 如何把正文段落、文档标题/文号/机构/地区/版本封装成可验证证据对象，同时避免用标题替代正文事实？如何记录多文档综合推论及其前提？
3. G3 这种部分归因失配如何局部修复？恢复后不足时是定向补搜、重新生成局部，还是明确保留缺项？失败上限、成本和超时如何控制？
4. 确定性计算、网络事实和知识解释如何进入同一回答契约？数值的地点、变量、单位、基准、时刻、批次、缺测与来源如何逐项校验？
5. 用户新追问怎样继承上下文中的台风、地区和日期，同时允许用户纠正？缓存怎样避免跨地点/跨日期串用？
6. 可参考 CRAG、Adaptive-RAG 和工具驱动智能体，但应基于已存在实现评估增量收益。若提出 skill，明确 runtime 加载、工具注册、权限、参数约束、失败/恢复与日志；单独新增 Markdown 不会改变 DeepSeek 行为。
7. 如何将评测分成“答案覆盖”“事实支持”“业务数值正确”“缺项诚实”“可读性”，避免同一个模型给自己打分形成虚高？如何验证源错配、日期越界、单位错误、未问缺项和恢复丢答案这些负例？

请对每一阶段列出文件/函数、数据结构、可执行伪代码、验收样例、回滚和依赖。不要直接承诺“160 题全部正确”，而是说明每个业务类型在哪些输入条件下可完整回答，哪些条件下需要缺项输出。

## 七 研究和开源参考

这些是供进一步核对的设计参考，不表示本仓库已运行它们或复现其指标：

- [CRAG 论文](https://arxiv.org/abs/2401.15884) 与 [作者仓库](https://github.com/HuskyInSalt/CRAG)，现有适配参考 commit `de7c2961ae624a1483a138c5798e1f6d0c4fb0e0`，见 `docs/CRAG_REFERENCE.json`。
- [Adaptive RAG 论文](https://aclanthology.org/2024.naacl-long.389/) 与 [作者仓库](https://github.com/starsuzi/Adaptive-RAG)：可评估路由复杂度与成本策略。
- [FloodOps](https://github.com/krishddd/floodops-multi-agent-system)：可评估连接器状态与任务编排；其 mock 回退不能用于冒充业务数据。
- [RapidResponseAgent](https://github.com/feizhao19/RapidResponseAgent)：可评估工具、案例检索、知识检索和核验的分工；代码可用范围与许可需复核。
- [RescueMind](https://github.com/BALADURGAG24/rescuemind-multi-agent) 和 [AWS geospatial agent 示例](https://github.com/aws-samples/sample-geospatial-agent-on-aws)：仅作工具接口/地理计算的实现参考，不直接替换本地业务数据。

没有同题同时间完整豆包输出，无法给出客观胜率，也不能知道其内部实现。现有截图能说明对方某些回答结构清晰，不能证明所有细节正确。方案应使用固定输入与独立评分比较方法，而不围绕某产品内部架构猜测。
